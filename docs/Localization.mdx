# Localization and app settings

`<SerupaProvider>` gives every component inside it a locale, the words the components say on their own, and extra icons. It's React context, so it reaches client components from a server layout, differs between concurrent server requests, and can change for one part of a page (ADR-0010).

```tsx
import { SerupaProvider, idLabels } from 'serupa-ds';

export default function RootLayout({ children }) {
  return (
    <html lang="id">
      <body>
        <SerupaProvider locale="id-ID" labels={idLabels}>{children}</SerupaProvider>
      </body>
    </html>
  );
}
```

| Prop | What it changes |
|---|---|
| `locale` | Every component that writes a date, time or number. Calendar, DatePicker, DateRangePicker and TimePicker: how dates and times are written and typed, month and weekday names, the first day of the week. NumberInput: how numbers are typed and shown. FormattedNumber, Meter, Progress, Badge counts, Pagination's page numbers, Stepper's step numbers, Input and Textarea's character counts, and ColorPicker's values: the locale's digits and signs. RelativeTime: "3 hari yang lalu". PhoneInput: country names. `useCollator`: how text sorts. Default: the browser's. A tag with an underscore, such as `en_US` from a server's `LANG`, is read as `en-US`; one Intl can't read at all is skipped for the browser's, with a warning in development, so a bad locale never breaks the page. |
| `labels` | The built-in words: close and dismiss buttons, loading text, pagination, date and time buttons, file upload text and so on (the `SerupaLabels` type lists every key). Pass `idLabels` for Indonesian, or only the keys you want to change. |
| `icons` | Icons that work by name inside it, in the shape `registerIcons` takes. |

## Language packs

Each language the package ships is an entry of its own, `serupa-ds/labels/<language>`, so an app loads only the languages it imports. A pack gives every built-in word (`labels`) and the locale it's written for (`locale`):

```tsx
import { SerupaProvider } from 'serupa-ds';
import { labels, locale } from 'serupa-ds/labels/id';

<SerupaProvider locale={locale} labels={labels}>{children}</SerupaProvider>
```

Packs ship for English (`en`, the default), Indonesian (`id`, the same words as `idLabels`), German (`de`), Spanish (`es`), French (`fr`), Portuguese (`pt`, Brazilian), Japanese (`ja`), Russian (`ru`), Chinese (`zh`, Simplified), Korean (`ko`), Italian (`it`), Arabic (`ar`, with `dir="rtl"` on the page), Turkish (`tr`), Hindi (`hi`), Vietnamese (`vi`), Dutch (`nl`), Polish (`pl`), Ukrainian (`uk`), Swedish (`sv`) and Malay (`ms`). `node tools/test/label-packs.mjs` checks each pack has every word, says something for each case (a count of one and of several, each reason a field can fail), and leaves nothing in English.

What wins, in order: the component's own prop (`dismissLabel`, `locale`, …), the nearest provider, an outer provider, then the defaults. A nested provider changes only the keys it sets.

## Labels that count

Some labels take a number, such as Combobox's `resultsCount` or Pagination's `page`. English needs two forms ("1 result", "2 results"); Russian needs three, Arabic six, Indonesian one. `plural(locale, count, forms)` picks the form with `Intl.PluralRules` and writes the count the locale's way where the words have `#`. Only `other` is required; a form left out falls back to it.

```tsx
import { plural, SerupaProvider } from "serupa-ds";

const ruLabels = {
  resultsCount: (n: number) => plural("ru", n, { one: "# результат", few: "# результата", many: "# результатов", other: "# результата" }),
};

<SerupaProvider locale="ru-RU" labels={ruLabels}>{children}</SerupaProvider>;
```

## Server-rendered pages

A server can't know the visitor's locale. Without a `locale`, the components that write dates, times and numbers render the server HTML in `en-US`, hydrate in `en-US` too so React sees no mismatch, and switch to the browser's locale right after. To show the visitor's format from the first paint, set the provider's `locale` from the request, for example from the `Accept-Language` header or the user's saved setting. Without one, the server logs a warning once ("Serupa: rendered on the server without a locale…") so the change after hydration doesn't go unnoticed:

```tsx
import { headers } from 'next/headers';

export default async function RootLayout({ children }) {
  // "id-ID,id;q=0.9,en;q=0.8" gives "id-ID". A "*", an empty header or none falls back to en-US.
  const first = (await headers()).get('accept-language')?.split(',')[0]?.split(';')[0]?.trim();
  const locale = first && first !== '*' ? first : 'en-US';
  return <html lang={locale}><body><SerupaProvider locale={locale}>{children}</SerupaProvider></body></html>;
}
```

## In your own components

`useSerupa()` gives the nearest provider's settings (`locale`, `labels`, `icons`, `platform`), and `useLocale(own?)` the locale the components use: `own` when given, else the provider's, else the browser's, always one Intl can read (`en_US` comes back as `en-US`). Use them so your components follow the same settings, for example `date.toLocaleDateString(useLocale())`. `announce(text)` says text through the same live regions the components use.

## Right to left

Set `dir="rtl"` with the language, `<html lang="ar" dir="rtl">`, and the components mirror: layouts use logical properties, and arrows and chevrons point the way reading goes. The stylesheets find the direction with `:dir(rtl)`.

A CSS minifier can rewrite that for older browsers. Lightning CSS, Vite's default minifier, turns `:dir(rtl)` into a list of right-to-left languages (`:lang(ar)`, `:lang(he)`, `:lang(fa)`…), so a page with `dir="rtl"` but no such `lang` (a test page, or a language not on its list) doesn't mirror its arrows. Setting `lang` fixes it, or tell Lightning CSS to keep `:dir()`:

```ts
// vite.config.ts (lightningcss comes with Vite; add it to devDependencies to import it)
import { Features } from 'lightningcss';

export default {
  css: { lightningcss: { exclude: Features.DirSelector } },
};
```

## Accessibility

Set `lang` on `<html>` (or on the element around a provider with another language) to match the words, so screen readers pronounce them correctly. The provider doesn't set it, because it renders no element.
