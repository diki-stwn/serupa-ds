# Tools

Everything needed to maintain Serupa: the test suite, the design tokens export, the custom icon build, the release script and the CSS trimmer. Nothing here ships to products; consumers only need the package: `tokens.css`, `dist/` and `fonts/`.

## Setup

Clone the repository, then from its folder:

```sh
npm install                       # the build (tsup, TypeScript), React, Playwright and Style Dictionary
npx playwright install chromium   # add firefox webkit to run the suite in those too
```

Node 26 (`.nvmrc`), which the package also requires (`engines`). TypeScript 7 type-checks the code (`npm run typecheck`). It has no compiler API yet, so the tools that load TypeScript as a library (typescript-eslint, tsup's `index.d.ts` bundling, the Public API check) get TypeScript 6's from `@typescript/typescript6`, the TypeScript team's package for this: `tools/typescript/api.mjs` points their `typescript` imports there. Drop it once they support TypeScript 7. Dependencies are pinned to exact versions; Dependabot (`.github/dependabot.yml`) opens grouped update pull requests every Monday, for npm and the GitHub Actions, and CI decides whether each one lands. CodeQL (`.github/workflows/codeql.yml`) scans the code and the workflows on every pull request and weekly. The workflows follow five supply-chain rules, which the Workflows check (`tools/test/workflows.mjs`) enforces: every action is pinned to a full commit SHA with its version as a comment (`actions/checkout@3d3c42e… # v7.0.1`; Dependabot bumps both), since a tag can be moved to other code; text a pull request's author controls, such as the branch name, reaches a `run:` script only through `env:`, never pasted in as `${{ … }}`; every checkout sets `persist-credentials: false`, so later steps (and the dependencies they run) find no token in `.git/config`, and a push gets its token for that one git call; a job that installs dependencies or runs the branch's own actions (`npm ci`, `npx`, `uses: ./`) gets no secrets and no `id-token: write`, so a hijacked package or a pull request's code never runs beside a token that outlives the job (the baselines and Release workflows each split into a job that runs the code with a read-only or job-only token and one that holds `BOT_TOKEN` and runs none of it); and Dependabot offers a release only once it is 7 days old (`cooldown`), the window in which a hijacked version is usually caught and pulled. Nothing else: Python is only needed to rebuild the Material Symbols from the font (`tools/icons/material.py`), which the font never changing makes rare. Whitespace is set in `.editorconfig` (UTF-8, LF, a final newline, 2-space indents, no trailing spaces except in Markdown), which most editors and coding agents read; there is no formatter, so match the code around a change (quotes, wrapping).

## Build

```sh
npm run build       # src/ → dist/ (tools/build/build.mjs: tsup for the JavaScript and types, then the CSS)
npm run typecheck   # tsc over src/ (strict), then tools/ and bin/ (JavaScript, checked from JSDoc)
npm run lint        # ESLint (TypeScript with type information for src/, React hooks rules, Vitest rules for the tests, no English words written into a component: tools/lint/, the tools) and Stylelint (the CSS; in a component's CSS also the system's conventions, tools/lint/stylelint-serupa.mjs: one dk.components layer, values from tokens, colors through the component's tokens, outline focus rings, class names as dk-block__element--modifier, no styling of another block's elements)
```

ESLint also checks accessibility on the components' and docs' JSX (eslint-plugin-jsx-a11y-x, taught what each Serupa component renders by `tools/lint/a11y-components.mjs`). The hits that were already there when it was turned on are listed in `eslint-suppressions.json`. That list only shrinks: a new hit fails, and so does one that's gone until `npx eslint . --prune-suppressions` takes it out.

`dist/` is build output: never edit it, and it isn't committed. The utility classes come from `src/styles/utilities.template.css`: `tools/utilities/build.mjs` expands its `@each` loops over the tokens in `tokens.json` (so a new color or spacing token gets its classes) and its `@responsive` list into the `sm:` … `2xl:` variants, writing `src/styles/utilities.css` (not committed); the build ships its masks and gradients apart, in `dist/utilities-extra.css` (`tools/utilities/extra.mjs` splits them off), and the rest as `utilities.css` and in `bundle.css`. The build, `npm run lint`, Storybook and Vitest run it first; `tools/utilities/template.mjs` describes the syntax. `tools/build/registry.mjs` writes `src/generated/` (not committed) from the component folders: the package's export list (each folder's `index.ts`), the CSS imports (in the order of `src/styles/cascade.txt`, then any other component A to Z) and the label sets (each folder's `labels.ts`). With `--readme` it rewrites the components index in `README.md` (each component under its Storybook group, with its guide's first sentence), which `tools/release.mjs` also does on every release. The build, `npm run lint`, `npm run typecheck`, Storybook and Vitest run it first.

## Test suite

```sh
npm test                                  # builds, then runs everything (about two minutes)
node tools/test/run.mjs                   # everything, against the dist/ you built last
node tools/test/run.mjs --update          # accept intended changes as the new baselines
node tools/test/run.mjs --browser webkit  # the suite in WebKit (or firefox); baselines are kept per engine
node tools/test/run.mjs --locale id-ID    # the suite with the browser in another language (CI adds one: all components on main; on a PR, the changed ones and the src/internal tests that render them)
node tools/test/run.mjs --compat safari   # add the cross-browser comparison (safari, firefox or webkitgtk)
node tools/test/run.mjs --list            # the steps it would run (with --group, of one group)
node tools/test/run.mjs --since main      # only the components changed since main, and the ones that use them
npm run test:unit                         # only the component tests (Vitest), straight from src/, in a few seconds
npm run test:watch                        # the same, re-running as you edit
npm run test:coverage                     # the same, and which lines they run (coverage/index.html); fails under the floors in vitest.config.ts
npx vitest run src/components/Checkbox    # one component's tests
npm run test:checks                       # the checks below (all but visual and Storybook), in Vitest; build first
npx vitest run tools/test/foundation.mjs  # one of them (or node tools/test/foundation.mjs, which prints its results)
npx vitest run --project checks -t contrast  # the checks whose name says contrast
```

On a pull request, CI runs `--since` its base: when every changed file is inside component folders (with their baselines, server-render case and changeset), the component tests, visual snapshots and Storybook checks cover only those components and every component that uses one of them; the checks always run whole. Any other change runs everything, and so does every push to main, which catches what a narrowed run missed. `affected.mjs` tests which components a change covers.

### Component tests

Each component's behaviour test sits next to it as `src/components/<Name>/<Name>.test.tsx`. They run in
[Vitest](https://vitest.dev) browser mode: a real Chromium through Playwright, so computed styles, focus and
the keyboard behave as they do for people (set `SERUPA_BROWSER=firefox` or `webkit` for another engine). They
render the components from `src/` with `vitest-browser-react`, find things the way people do
(`page.getByRole('checkbox', { name: 'Newsletter' })`), and each `test()` names one behaviour, so a failure
says which one broke, with the expected and received values and a screenshot. Shared helpers (resolved
colors, WCAG contrast in all six themes) are in `tools/test/vitest/helpers.ts`.

Every component has its own `<Name>.test.tsx`, and a new component needs one: the contract check fails
without it. `npm run new-component -- <Name>` (`tools/new-component.mjs`) writes a starting test with the
rest of the folder; `tools/test/new-component.mjs` checks that what it writes passes the contract. setup.ts turns transitions and animations off, so a test reads end states; a test about motion
turns them back on with `withMotion()` (one read or one test) or `keepMotion()` (the whole file). It also starts each test file at the stories' clock (`CLOCK` in `lib.mjs`, 12 March 2025, ticking from there), so a test of today's date or a relative time doesn't depend on the day the suite runs; `vi.useFakeTimers` still fakes `Date` on top of it.

Every story is also rendered to HTML in Node, as a server would (`tools/test/vitest/serverStories.ts`, on the same clock, standing still). `src/internal/hydrateStories.test.tsx` hydrates that HTML in the browser and fails on any mismatch, `src/internal/hydrateStoriesCsp.test.tsx` hydrates it again on a page with `style-src-attr 'none'` and fails when any element's box differs from the story rendered in the browser (a style the policy dropped that the component doesn't set again), and `src/internal/serverHtml.test.tsx` compares it with `tools/test/baseline-server/<Component>.html`: each story under a comment with its name, one tag per line, so a change to what a server sends shows in the pull request as a diff of a few lines. When the change is intended, run `npm run test:server-html:update` and commit the new baselines with it. They're plain text from Node (the version in `.nvmrc`), so they're the same on every machine.

`src/internal/ariaStories.test.tsx` draws every story in the browser and compares the page's accessibility tree (Playwright's `ariaSnapshot`: roles, names, states and nesting, as a screen reader gets them) with `tools/test/baseline-aria/<Component>.yml`. A lost name or a changed role shows as a short diff even when the picture looks the same. The shared live regions are left out, since what they hold depends on the stories before. The baselines are Chromium's in English, so Firefox, WebKit and locale runs skip it. When a change is intended, run `npm run test:aria:update` and commit the new baselines with it.

`src/internal/tabWalk.test.tsx` walks every story with Tab and then Shift+Tab, from a button before it to a button after it (WCAG 2.1.2, no keyboard trap). Focus has to get through and out both ways, and must never land inside `aria-hidden` or `inert` content. When focus goes round in circles, as in an open modal, the test presses Escape, the way out a modal offers, and that has to let focus go.

`src/internal/leaks.test.tsx` mounts and unmounts every story three times. What's left behind afterwards must not grow from the first time to the third: listeners on `window`, `document`, `<html>` or `<body>`, intervals, ResizeObserver, MutationObserver and IntersectionObserver instances that were never disconnected, and elements left in `<body>` or `<head>`. Something made once and shared, such as the live regions, is fine. It watches from inside the test's own frame, since a heap count would take in the other test files' frames that share the page.

`src/internal/layoutShift.test.tsx` puts each story's server HTML on the page with the stylesheets, hydrates it, waits for `document.fonts.ready` and two frames, and adds up the layout-shift entries in that time (Chromium only). Any shift fails: it is a page that jumps under the pointer when it hydrates. The stories that measure their width after mount and wrap, stack or cut to fit are in `KNOWN`, each with its reason, and may move up to 0.03. An entry comes out when its component's fix lands.

`src/internal/mountTime.test.tsx` mounts every story five times under React's Profiler and keeps the fastest. A story that takes longer than 20 ms to mount fails. That's React's development build, where the slowest story takes about 9 ms and most take under 4. The PhoneInput stories that show four or six fields, each listing 244 countries, have budgets of their own in `OWN_BUDGET`. A component whose story is heavier on purpose gets its own line there, with the reason.

`src/internal/inp.test.tsx` times what Interaction to Next Paint counts, through the browser's Event Timing, for opening and typing into Combobox (its Playground, and one with 10,000 options), opening Dialog, opening and closing Menu, and picking with the keyboard in Select. Each answer must paint within 100 ms. One takes a frame or two here, so the budget catches a change that makes it several times slower, such as rebuilding every option on each keystroke.

`src/internal/network.test.tsx` shows every story and fails on any network request the story makes of its own: a `fetch`, an `XMLHttpRequest`, a `sendBeacon`, a `WebSocket` or an `EventSource`, or markup that loads from another origin (an `src`, `srcset`, `poster`, a stylesheet or preload `<link>`, a `url()` in a style attribute). The page's own files and `data:` URLs are fine. An app with a strict CSP, an offline page or a privacy review shouldn't find the design system calling out.

`src/internal/strictCsp.test.tsx` shows every story on a page with the strict policy that the getting-started page promises works: `script-src 'self'; style-src 'self'; font-src 'self'`, with no `'unsafe-inline'` and no `'unsafe-eval'`. Any violation the browser reports fails the story, and so does an inline event handler or a `javascript:` URL in its markup, since those are only reported once they run. What a server render needs on top of this is covered by `serverStyles.test.tsx`.

`src/internal/trustedTypes.test.tsx` shows every story with Trusted Types on (`require-trusted-types-for 'script'`), where the browser refuses any string written as HTML or script (`innerHTML`, `insertAdjacentHTML`, a script's text, `eval`) that no policy made. Any violation fails the story, so an app that turns Trusted Types on needs no policy for the design system. Custom icons, which the stories don't have, are checked the same way by `icons.mjs`. Browsers without Trusted Types skip it.

`src/internal/activity.test.tsx` shows every story inside React's `<Activity>`, then hides it, as an app does with a tab or route it keeps alive. Once hidden, nothing the story put elsewhere may still be on screen (a portal in `<body>`, the top layer), no interval it started may still run, and no animation-frame loop may keep going. The stories open no overlay at rest, so an open Dialog, Drawer, Popover, Menu, Tooltip and Toast are checked the same way.

`src/internal/motion.test.tsx` is the motion quality gate (EH1). It looks at every animation each story runs, on mount and after it's used (opened, toggled, hovered), with and without reduced motion. Nothing may animate a layout property (width, height, inset, margins, gaps, grid tracks). A loop may not repaint on every frame (colors, shadows, `stroke-dash*`, `background-position`). A surface that can be closed mid-way must not enter with keyframes. Nothing may transition on the first frame after mount. Under reduced motion, only fades are allowed. A popup placed beside its trigger that scales must grow from the edge facing that trigger, and nothing may keep `will-change` once its motion has ended. Frame times under CPU throttling aren't gated, because in a headless browser every animation runs at the same 33 ms a frame, an opacity fade included. Today's breaches are listed in `KNOWN` under the queue item that fixes each one, and a line whose breach is gone fails the run until it's removed, so the list only shrinks.

These story-wide tests (hydration, server HTML, accessibility tree, keyboard walk, leaks, layout shift, mount time, network, strict CSP, Trusted Types, Activity, motion) also run on a pull request that only touches component folders, on those components' stories (`SERUPA_ONLY`, through `storiesToRun()` in `tools/test/vitest/stories.tsx`). A component's baseline is checked before it reaches main, not after.

cross-browser comparison and the visual and Storybook steps, which `run.mjs` shards across CI jobs. Each result a
script passes to `report()` is one test, so the checks share the component tests' reporter, `-t` filter and watch
mode, and a new script is picked up with no entry anywhere. Run with `node`, a script prints its results and exits
1 on a failure, as before.

When a test fails, it names what changed. If the change is intended, run with `--update` and commit the new baselines with the change.

**Baselines belong to CI.** Screenshots and computed styles differ a little between machines (fonts, anti-aliasing), so `baseline-visual/` and `baseline-utilities.json` are rendered on GitHub's runner: add the `update-visual-baselines` label to a pull request and the Update baselines workflow commits new ones to its branch. Locally, Visual snapshots can fail for that reason alone. Utility classes don't depend on the installed fonts (the page's line height is fixed), and a CHANGED class prints what changed, property by property, or what it does now when its effect is too long to keep as text.

**When `tokens.json` or `tokens.css` is reported out of date:** the tokens are written in `tokens/serupa.tokens.json` (the W3C format, ADR-0014); `tools/tokens/source.mjs` makes `tokens.json` from it and `tools/tokens/build.mjs` makes `tokens.css` from `tokens.json`. Run `npm run tokens` (or `npm run build`, which runs it first) and commit the generated files with the source change. CI checks they match.

**Changing a token in the source:** change its `$value` (`{ "value": 0.25, "unit": "rem" }`, a color's `components` and `hex`). A token whose CSS isn't how its `$value` prints keeps it in `$extensions["com.serupa"].css` (`"5%"` for the number 0.05, a shadow written with `rgb()`): change both, or take `css` out to have `$value` printed. The check names a `css` that no longer means its `$value`. A value per theme sits in `$extensions["com.serupa"].themes`, `contrastMore` and `compact` beside it; the type styles and fonts in the root's `$extensions`.

## Releasing a version

Releases run on GitHub, from changesets (`.changeset/README.md` has the details):

1. **Each pull request** that changes what projects get adds a changeset: `npx changeset` (patch, minor or major, and a note whose lines start with Added, Changed, Fixed…).
2. **On `main`**, the Release workflow keeps a pull request called "Release: next version" open. It runs `npm run version-packages` (`tools/version.mjs`): the notes go into `CHANGELOG.md` under the new version, and `tools/release.mjs` stamps the version into `package.json` and the install lines in `README.md` and `docs/GettingStarted.mdx`. Everything else takes it from `package.json` at build time: `dist/`, `Serupa.version`, and the `__VERSION__` in the headers of `src/styles/base.css` and `src/theme.js`.
3. **Merging that pull request** releases it: `npm run release` (`tools/publish.mjs`) tags `vX.Y.Z` and makes a GitHub release with the notes and the package (`npm pack`) attached, its SHA-256 under the notes. The workflow's attest job then signs that file with a build-provenance attestation (`actions/attest-build-provenance`), in a job of its own that runs none of the repository's code, since `id-token: write` lets a job sign for the repository; `gh attestation verify <file> --repo diki-stwn/serupa-ds` checks it.

The workflow needs one repository setting: Settings → Actions → General → Workflow permissions → **Allow GitHub Actions to create and approve pull requests**. Pull requests the workflow opens don't start CI themselves; the changes in them are the changelog and version numbers.

A pull request that changes what the package ships needs a changeset: the Changeset workflow runs `node tools/changeset-check.mjs <base>` and fails without one (label the pull request `no-changeset` when the change ships nothing new). It reads each changeset with `tools/changesets.mjs`, the same reader the release uses, so a changeset the release couldn't read (no front matter, or no bump for this package) fails the pull request instead of the Release workflow on main. It also checks the bump against the public API: an export, token (`tokens.json`) or utility class (`tools/test/baseline-utilities.json`) that goes away needs a major, and a new one, or a change to the exported types, at least a minor.

By hand, without GitHub: write the notes under `## [Unreleased]` and run `node tools/release.mjs minor` (or major, patch, or a number). `node tools/release.mjs --check` checks that every file carries the same version (CI runs it), and that `CHANGELOG.md` ends with the link definitions its headings give (`tools/changelog.mjs`): each `## [x.y.z]` links to the compare from the version before it, the oldest to its tag, and `[Unreleased]` to everything since the latest. Every release writes them; `node tools/release.mjs --links` does it by hand. Versions that were never tagged (most before the 5.0.0 rename, and 6.0.0 and 7.1.0) are headings without brackets, so they ask for no link. The README's Versioning section says which kind of release a change needs.

## Design tokens export

```sh
npm run tokens                                       # after changing tokens/serupa.tokens.json: tokens.json, tokens.css and design-tokens/
node tools/tokens/source.mjs                         # tokens.json only (--check: exit 1 if it's out of date, or the source is wrong)

node tools/tokens/export.mjs                         # design-tokens/ only (--check: exit 1 if it's out of date)

node tools/tokens/figma-variables.mjs               # what the Figma variables workflow would send (--send with FIGMA_TOKEN and FIGMA_FILE)

```

`export.mjs` writes the W3C Design Tokens files (see the README). The Style Dictionary config changes two of Style Dictionary's defaults so its output matches `tokens.css`: it writes the format's duration objects (`{ "value": 150, "unit": "ms" }`) in their own unit instead of seconds, and it uses the system's own variable names (from `$extensions["com.serupa"].cssVar`). Add platforms to it for iOS, Android or Sass.

## Fonts

```sh
python3 -I tools/fonts/subset.py    # split fonts/InterVariable*.woff2 by script, and list the faces in tokens.json (needs fonttools, brotli)
node tools/fonts/fallback.mjs       # measure Inter against Arial in Chromium and list the Inter Fallback faces in tokens.json (needs fonts-liberation on Linux)
npm run tokens                      # then write their @font-face rules into tokens.css
```

`Inter Fallback` comes right after Inter in `--font-sans`: Arial (or Helvetica, Liberation Sans, Arimo) with `size-adjust` and Inter's ascent and descent, for the latin range only. It draws the text until Inter arrives, at almost the same width, so the page doesn't move when Inter swaps in.

After Inter, `--font-sans` names Noto Sans Arabic, Hebrew, Devanagari and Thai (143). They aren't shipped: a device that has them uses them, and each draws only its own script, so the browser picks the right one for each character whatever the `lang`. Han characters are drawn differently in Japanese, Korean and Chinese, so under `lang="ja"`, `"ko"`, `"zh"` and `"zh-TW"` (or `zh-Hant`) `--font-sans` puts that language's Noto Sans CJK first. Marks above and below the letters need room: under those langs every `--text-*--line-height` is at least 1.6 times the font size for Arabic and 1.5 for Devanagari, Thai and CJK. The list is `type.scripts` in `tokens.json`.

Each script gets its own file with Google Fonts' `unicode-range` for it (latin, latin-ext, cyrillic, cyrillic-ext, greek, greek-ext, vietnamese), and `symbols` takes every other character Inter draws, so a page downloads only the scripts its text uses. All features, the variation axes and the names stay. Run it again only when a font in `fonts/` changes. `size.mjs` holds the latin files to their size.

## Trimming CSS for production

```sh
node bin/serupa-purge.mjs src/ public/index.html -o dist/bundle.min.css   # in a project: npx serupa-purge …
```

Scans the sources for class names and writes a copy of `bundle.css` with only the rules they need, plus the component styles, keyframes and variables. A typical page keeps the component styles (about 220 KB) and a few KB of utilities, instead of nearly 2 MB. Class names built at runtime (`"grid-cols-" + n`) can't be found; list them with `--keep grid-cols-2 grid-cols-3` or `--keep @safelist.txt`.

## Storybook

```sh
npm run storybook         # the documentation at http://localhost:6006, updating as you edit
npm run build-storybook   # a static copy in storybook-static/ (CI builds it and the Storybook test opens every page)
```

Storybook is the system's documentation. `.storybook/` holds its setup (the brand and mode toolbar sets `data-theme`, with the brands taken from `tokens.json`; the Motion menu slows every duration and delay token ×4 or ×10, to watch an animation frame by frame; the Content menu swaps a story's sample data for the worst case, none or one, from `.storybook/content.ts`, for stories that read it with `usePeople()`; the Accessibility addon checks each story). The pages are in `docs/` (introduction, getting started, foundations, versioning, changelog) and `src/components/<Name>/<Name>.mdx`; they read `tokens.json`, the README and each component's `README.md`, so they can't drift. Stories are `src/components/<Name>/<Name>.stories.tsx`, one per state and variant.

## Rules the tests enforce

- Components and utilities read tokens; no value is written out when a token holds it. The documented exceptions are breakpoints inside `@media` (which must still be `screen-*` values), shadow shapes (so color classes can recolor them) and `rounded-full` (9999px).
- Shared tokens are read as `var(--token)`, with no fallback value: `tokens.css` always loads first. Component tokens keep their default: `var(--button-bg, var(--primary))`.
- Tokens, page defaults, components and utilities each sit in their cascade layer (`dk.tokens`, `dk.base`, `dk.components`, `dk.utilities`), declared in that order at the top of every file.
- Utility classes keep the same names and effects; a change is deliberate and goes with an updated baseline.
- The system loads nothing from other servers.
- The token source's `themes` (`$extensions["com.serupa"].themes` in `tokens/serupa.tokens.json`, `color.themes` in `tokens.json`) is the one list of brands and themes. Adding a brand means adding its `<brand>-light` and `<brand>-dark` themes there, then `BRANDS` in `src/theme.js`, `ThemeBrand` in `src/theme-types.ts` and the theme lists in the tests; the foundation audit names any that's missing.
